## 直接证据

### 1. 空抓发生时，手臂参考本身也未到瓶子附近

`g1_tcp_fov58_vla01` 在评估约31.2秒出现闭爪。闭爪期间的最近一次采样显示：

- 实际 TCP 距瓶身中心约 **28.6cm**；物理日志采样的最小值约28.5cm。
- 同时发出的上半身参考动作在实测基座/下肢上做 FK，距瓶身中心仍约 **31.7cm**。
- 同时刻参考 FK 与实际 TCP 相差约 **3.8cm**；整轮平均差约2.5cm，包含控制响应滞后。

这排除了“只是手臂慢了一点，正确的抓取参考已经到位”这一解释。
它仍可能涉及视觉到动作的匹配、策略预期的走近与实际位移不一致，不能据此断言唯一根因。
该 FK 使用实测基座，不能代表策略未来预期的整个身体平移。

对应结果：`results/tcp_alignment/vla58_01/tcp_tracking_summary.json`。
带实测距离、夹爪命令和双指力的录像：
[官方 VLA 空抓片段](results/tcp_alignment/official_vla_excerpt.mp4)。

### 2. 碰倒瓶子可以追踪到单指提前接触

单独的 G1 TCP 标定对照 `g1_tcp_calibration02` 捕获了200Hz接触事件。
**这是使用仿真状态的标定参考，不是 VLA，也没有成功完成任务。**

首次接触时，瓶身中心在实际夹持中心坐标系中约为：

```
x = +49.4mm，y = +18.4mm，z = -27.0mm
```

当前手指有效纵向范围约±45mm；全开内部间距96mm，瓶身直径60mm，
未倾斜、未偏航时允许的中心横向余量只有 `(96−60)/2 = 18mm`。
首次碰撞已经处于前端/侧向边界：`rh_pad_a` 单指接触瓶身，另一指力为0。
首次力约0.265N，该对照随后最大工具接触力约1.438N。
夹爪当时仍在全开状态，瓶子被推走，未形成持续夹持。

这说明“图像里已靠近”并不保证瓶子已进入实际双指夹持区；厘米级跟踪/外参偏差足以造成碰瓶。
它解释的是同一物理模型中的碰撞机制，不冒充对上一轮某次随机 VLA 轨迹的精确复现。
旧动作回放受不同起步位姿影响，没有重现原来那次接触，也保留了该失败结果。

[碰瓶诊断录像，明确标注 NOT VLA](results/tcp_alignment/contact_diagnostic_not_vla.mp4)
和 [原始接触事件](results/tcp_alignment/calibration02/contact_events.json)。

### 3. 工具安装松动不是主要误差来源

实际夹持中心由两个物理指垫的中点定义，腕坐标下为 `[0.125,0,0]m`：
工具安装0.060m + 指垫中心0.065m，与原 TCP site 一致。
使用自由工具刚体的真实位置计算 TCP，并与腕部 site 比较，首次诊断最大偏差约0.52mm。
因此没有通过随意平移 TCP 去追瓶子；主要误差远大于工具焊接约束的偏差。

## 本轮修改

1. **腕部相机到夹指的投影拟合。** 公开示范里夹指尖端在画面下半部；
   旧相机在640×480坐标下把内侧尖端投到约v=54，示范右侧约v=300，偏差约250像素。
   采用公开视频中静止于相机坐标的夹指顶部角点拟合左右相机近似安装位姿。
   同时把替代夹指厚度从12mm调整为7mm，保留6–96mm实际开合范围和真实碰撞。
   用于拟合的手工角点重投影 RMS 左约1.0px、右约3.1px。
   这个数值不包括手工标注误差、真实夹指形状误差，也不证明恢复了真实手眼标定。

   [投影检查图](results/tcp_alignment/camera_projection_check.png) 红色为原内侧尖端、
   蓝色为拟合后的投影、绿色为手工标记，星号表示替代模型 TCP 的投影。
   抓取中心并不等于图像中心，甚至可能位于图像下边界之外。

2. **保持时间单位的50Hz传输。** 原遥操作 `pico_thread.py` 默认50Hz，
   原 C++ WBC 控制周期20ms，而原 VLA 客户端以30Hz发送。
   新增 `TimedPoseStream`：保留模型30Hz动作时间，按时间戳插值身体关节到50Hz；
   夹爪保持离散命令，根部yaw速度按50Hz正确积分。
   实际发送频率约50.000Hz，没有通过把模型动作加速到50Hz来完成任务。

3. **评估另一种推理执行方式。** 新增 `hold`：推理期间保持末次姿态，返回后从动作块第0帧执行，
   并让保持期间的yaw速度为0。这样不需要假设新旧未做 RTC 的预测轨迹一致，
   也不跳过前13帧预测。模型仍预测50帧、执行前25帧。
   该组客户端循环约29.82Hz；其中包含等待推理的保持tick，不能称为全部动作都以30Hz推进。
   例如58°第一轮788个保持tick，实际非保持动作推进约21.07Hz。

4. **标准化真正的起步位姿。** 一轮发现落地后根部后移到x≈−0.23m，显著增加瓶子的相对距离。
   上一轮的 IK 可达性来自另一站姿，不能证明每次实际试验都可达。
   新协议在落地稳定后、评估开始前，把机器人和刚性安装工具整体平移回起步原点，
   不移动平台、瓶子或垃圾桶；再稳定1秒，检查站立及原点偏差。
   平移和前后位姿保存在 `initial_placement.json`，真正初态保存在 `initial_state.json`。
   初始化在录像中明确标注，评估期间没有位姿重置或物体附着。

5. **三维诊断和观测记录。** 增加每帧qpos/qvel及monotonic时间、实际/腕部TCP、
   指垫中心、开口、瓶子相对TCP位置、200Hz接触几何事件、50Hz真正发送的参考动作。
   `analyze_tcp_tracking.py` 按时间戳对齐发出的参考与实际状态；旧记录只能近似对齐，会单独标记。

6. **修正抓取判据的近邻检查。** 改为实际工具 TCP 到完整瓶子包围盒的距离，
   避免只检查瓶身原点而拒绝靠近瓶颈的真实接触。
   仍必须满足闭合命令、双指各>0.2N持续0.15秒、抬升和松手后稳定入桶。
   这没有让本轮失败试验变成成功。

## 相机仍不能称为精确标定

仓库 README 明确为腕部D405、头部SV1-25；`assets/` 有两个安装支架 STL，
但没有实际640×480内参、左右设备序列号绑定、腕关节到光心的手眼矩阵和完整 CTAG TCP 装配变换。
单个支架 STL 的局部坐标不能自动确定这些装配关系。

D405 官方产品页给出的标称RGB/深度视场角为87°×58°，
因此另行使用58°垂直FOV先验拟合和测试。
[RealSense 官方规格](https://www.realsenseai.com/products/stereo-depth-camera-d405/?query-1b67a595-page=1)。
**58°仍是产品标称先验，不是本项目640×480流的实测 fx/fy/主点和畸变。**

75°与58°两种先验都能把同一组共面角点拟合到近似相同的1–3px残差，
却得到相差数厘米的相机安装位置。这说明只靠这些角点不能唯一恢复实际度量外参。
目前的鱼眼头部投影、合成场景外观、CTAG替代几何也继续存在分布差异。

## 复测与获得真正的内参

服务器复测（先选择空闲控制器GPU，GPU策略服务仍在127.0.0.1:18006）：

```bash
cd /mlplatform/OpenHLM-repro
TASK_SCENE=bottle-bin CAMERA_PROFILE=approximate-fisheye TOOL_PROFILE=visual-fit \
WRIST_CALIBRATION_FILE="$PWD/reproduction/pi05/wrist_camera_nominal58_fit.json" \
EXECUTION_MODE=hold TRANSPORT_HZ=50 STANDARDIZE_START=1 CONTROL_GPU=4 \
EVALUATION_SECONDS=90 RUN_NAME=g1_tcp_new_trial \
  bash reproduction/pi05/run_sim_evaluation.sh vla
```

提供了 `capture_d405_intrinsics.py`。应在连接相机的主机上、设备未被其他进程占用时执行，
它只打开相机并读取录制分辨率的真实内参，不向机器人发送动作：

```bash
python capture_d405_intrinsics.py --width 640 --height 480 \
  --left-serial LEFT_SERIAL --right-serial RIGHT_SERIAL --output d405_intrinsics.json
```

脚本导出 fx/fy、主点、畸变、分辨率和序列号；它没有凭空补齐手眼外参。
真正继续精确对齐还需要腕关节→相机、腕关节→TCP的实测变换或完整装配标定数据。
在获得这些数据之前，本轮只能报告已修复确定的软件/起步偏差并完成近似对照，不能报告任务已修复成功。
